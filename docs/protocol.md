# Daemon protocol, version 3

Every factobot client (the `fac` CLI and the Python package; an MCP server later, decision 7) talks to the daemon with this protocol. The Rust types in `crates/factobot/src/protocol.rs` are the reference implementation; change both together and bump the version on any breaking change.

## Transport

Newline-delimited JSON over Unix stream sockets. A connection carries any number of requests; the daemon answers each one, in order, with one line.

The daemon listens on two sockets that speak the same protocol:

| Socket | Who gets it | Methods |
|---|---|---|
| Agent socket | Agents (through `fac`) and the harness | [Agent methods](#agent-methods) |
| Dev socket | The harness and developers only; never mounted into an agent sandbox | Agent methods plus [dev methods](#dev-methods) |

Agent socket path, first match wins:

1. `--socket` flag (CLI) or the `socket_path` argument (Python).
2. `FACTOBOT_SOCKET`.
3. `$XDG_RUNTIME_DIR/factobot/fac.sock`.
4. `$TMPDIR/factobot-$USER/factobot/fac.sock`.

Dev socket path: `--dev-socket`, then `FACTOBOT_DEV_SOCKET`, then `dev.sock` in the agent socket's directory. Because the default puts both sockets in one directory, an agent sandbox must mount the agent socket file alone (or the harness must pass a separate `--dev-socket`); the separation rests on that.

The daemon creates a missing socket directory with mode 0700. It appends every call on either socket to `<run dir>/calls.jsonl`: `unix_ms`, `duration_ms`, `surface` (`agent` or `dev`), the game `tick` the mod answered at (for rejected and failed calls too; null when the call never reached the mod or its reply was unreadable), `method`, `params` and the full `response`, except that a `screen` result's `png_base64` is left out and its length in characters logged as `png_base64_bytes`, so the log doesn't grow by megabytes per picture.

## Request

```json
{"v": 3, "id": 7, "method": "status", "params": null}
```

| Field | Type | Meaning |
|---|---|---|
| `v` | integer | Protocol version. The daemon rejects any other value with `bad_request`. |
| `id` | integer | Chosen by the client; echoed in the response. |
| `method` | string | See [Methods](#methods). |
| `params` | any | Method arguments; `null` or omitted when there are none. |

## Response

```json
{"v": 3, "id": 7, "ok": true, "result": {}}
{"v": 3, "id": 7, "ok": false, "error": {"code": "unknown_method", "message": "unknown method \"jump\""}}
```

An answer to an agent method that reached the game also carries `hud`, on success and on error alike (decision 75): what a player's screen always shows.

```json
{"v": 3, "id": 8, "ok": true, "result": {}, "hud": {"time": "1:23:45", "free_slots": 19, "research": "logistics 43%", "warnings": ["research has not moved for 6 minutes: the labs lack science packs or power"]}}
```

| Field | Meaning |
|---|---|
| `time` | The game clock, `h:mm:ss` since the map began. |
| `free_slots` | Empty slots in the agent's main inventory. |
| `research` | The current technology and its progress, or `none`. |
| `warnings` | Left out when there are none. One sentence each: 3 minutes or more of game time passed since the agent's previous command; 8 or fewer inventory slots are free; the body stands on a transport belt, underground belt or splitter, which carries it along; the current research has not moved for 2 minutes or more, or nothing is queued, while the agent has a lab; an electric network with a pole within 32 tiles of the body gets less power than its machines ask for; machines within 32 tiles show a warning icon (`not_plugged_in_electric_network`, `no_fuel`, `no_minable_resources`), counted per status with the nearest of each. |
| `warnings_still_true` | Left out when zero. How many warnings hold now but are not in `warnings` because the same condition was warned of in the last 20 seconds of game time, even with other numbers in its sentence (decision 82). |

`status` and `screen` carry no `hud`. A `wait` carries the one from its last look at the job; the polls before that leave the HUD alone.

Every agent method that reaches the game takes an optional `hud` param, for `fac --wait` (decision 82). `"skip"` answers without `hud` and leaves the HUD as it was: the warnings stay unsaid and the silence clock keeps running. `"defer"` answers without `hud` too, but counts as a command for the silence clock and keeps the warnings it would have given; the next answer with a `hud` gives them first, in their sentences as they were then, and does not repeat or count them again. A call the game refused (`ok: false`) ignores `"defer"` and carries its `hud` as usual. Any other value is `bad_request`. `fac walk`, `mine`, `craft` and `place --to` with `--wait` start the job with `"defer"`, then `wait` polls it with `"skip"`, so the printed answer holds the start's warnings, the time that passed before it among them, ahead of those that appeared during the wait.

| Error code | Meaning |
|---|---|
| `bad_request` | The line was not a valid request, used another protocol version, or had missing or out-of-range params. `id` is 0 when it could not be parsed. |
| `unknown_method` | No such method. |
| `rejected` | The game's rules forbid the action: out of reach, recipe locked, missing ingredients, nothing to mine. The message says which rule and by how much. A locked recipe names the technology that unlocks it (decision 66). An out-of-reach message ends `; you are at X, Y; from X2, Y2 you could reach it`: the point on the straight line from the target to the agent 1.5 tiles inside that reach, so a walk there ending within its default 1 tile reaches (decision 56). It is geometry only and may fall in a building or water. |
| `game_error` | The game or the factobot mod failed to run the call (a bug, not a rule). |
| `unavailable` | The daemon could not reach the game, or the agent has no body. The `fac` CLI also uses this code when it cannot reach the daemon. |

## Agent methods

### `status`

No params. Returns:

```json
{
  "daemon": {"version": "0.1.0", "protocol": 3},
  "game": {
    "tick": 227,
    "tick_paused": false,
    "speed": 1,
    "game_version": "2.1.24",
    "mod_version": "0.5.0",
    "connected_players": 0
  }
}
```

The other agent methods act through the agent's body, a playerless `character` (decisions 30 to 37, 39 to 42, 49 to 63 and 66 to 73). Positions are map tiles `{"x", "y"}`, x east and y south. Every collection in a result is a JSON list, empty or not.

### Jobs

`walk`, `mine`, `craft` and `place_line` start a job and return it at once; the job then runs in game time. Walking, mining and placing a line use the body, so starting any of them cancels the running one (`state: "cancelled"`, `error` says why), and the new job names it in `cut_short` `{"id", "kind"}` (decision 84). Crafts run in the character's hand-craft queue alongside them, first in first out.

A job is `{"id", "kind", "state", "started_tick", "ended_tick", "error"}` plus fields by kind. `state` is `running`, `done`, `failed` or `cancelled`; `ended_tick` and `error` appear once it has ended.

| Kind | Extra fields |
|---|---|
| `walk` | `target`, `position` (latest), `distance_walked` |
| `mine` | `target {"name", "position"}`, `count` (resources only), `mined` `[{"name", "count"}]`: what the inventory has gained of the target's products since the job started, so crafts that use those items meanwhile lower it |
| `craft` | `recipe`, `count`, `used` `[{"name", "count"}]` (what the craft took from the inventory when it was queued: ingredients, including intermediates the agent carried, which the game uses before it crafts more), `crafts_ahead` (crafts left in the queue until this job is done, its own included), and while it runs `eta_tick`: the tick it should be done on, from the craft time of each craft ahead at the character's crafting speed |
| `place_line` | `item`, `from`, `to` (the snapped first end and the last building, which is the snapped far end unless the line stops one step short of it), `direction`, `tiles` (buildings the line has), `placed` (put down by this job), `already_there` (the same building facing the same way was there, nothing used), `next` (where the next one goes; left out once all are down), `position` (latest), `distance_walked`, and `stopped_short` once every building is down but the walk beside the line couldn't reach the far end: why, and how many tiles the body stands from the last building |

| Method | Params | Result |
|---|---|---|
| `observe` | `{"radius", "problems"}`; `radius` 1 to 32, default 10 (32 with `problems`); `problems` true or false, default false | `{"position", "reach": {"build", "interact", "mine"}, "inventory": [{"name", "count"}], "crafting": [{"recipe", "count", "prerequisite"}], "jobs": [running jobs], "radius", "entities": [{"name", "type", "position", "direction", "status", "missing", "item", "underground", "paired_with", "lanes", "fill"}], "entities_not_shown", "resources": [{"name", "tiles", "amount", "nearest", "distance"}]}`. Entities are the nearest 50 within the radius, nearest first, other than resources, the agent and scenery (corpses such as tree stumps and remnants); fish in the water (type `fish`) are included. Fields that don't apply are left out: `direction` is shown for buildings that face a way; `status` is the game's entity status, as in `inspect`, for machines whose status a player sees as an icon (assemblers, furnaces, drills, inserters, labs, boilers, steam engines, pumps and the like); `missing` lists the ingredients a machine short of them lacks, as in `inspect`; `item` names the item of an `item-on-ground`; an underground belt shows `underground` and `paired_with` as `inspect` does. A straight run of two or more transport belts of one name facing one way, each feeding the next, is one entry with `from` and `to` (its first and last tile in the direction items travel) and `tiles` in place of `position`, and counts as one of the 50. A belt run, underground belt or splitter with items on it shows `lanes` `{"left": [{"name", "count"}], "right": [...]}`: the total of each item lying on each lane of its tiles, facing the way items travel, so two items on one lane show at a glance (decisions 62 and 73); it is left out when there is nothing on either lane. A belt run or single transport belt shows `fill`, the items on it over the most its tiles hold (4 a lane per tile of the lane's length, so 8 on a straight tile), from 0 for empty to 1 for packed (decision 71). Resources are summed per kind; water tiles are listed among them as `water`, with no `amount`. With `problems` true the result is `{"position", "radius", "machines", "entities": [{"name", "type", "position", "direction", "status", "missing"}], "entities_not_shown"}` instead: only the agent's machines (the kinds that show `status` above) within the radius whose status is not `working` or `normal`, nor, for an inserter, `waiting_for_source_items` or `waiting_for_space_in_destination`, nearest first, at most 50, with `machines` the number of the agent's machines it looked at (decision 72). |
| `inventory` | `{"items"}` optional, a list of item names | `{"inventory": [{"name", "count"}]}`: the agent's main inventory, as in `observe`, or only the named items in the order given, with count 0 for one it has none of. `rejected` for a name that is no item, or for a fluid, which is not carried (decision 66). |
| `stats` | `{"items"}` optional, a list of item or fluid names | `{"items": [{"name", "fluid", "made_1m", "used_1m", "made_10m", "used_10m", "made", "used"}], "idle": [names]}`: the force's production statistics on the agent's surface, as the production window shows them (decision 68). `made_1m` and `used_1m` are per minute averaged over the last minute, `made_10m` and `used_10m` over the last 10 minutes (a world younger than a window counts nothing before it began), and `made` and `used` are the totals since the map began. `fluid` is true for a fluid and left out for an item. Hand-crafted products count as made and what hand-crafting uses up as used. With no `items`, every item and fluid made or used in the last 10 minutes, busiest in the last minute first, and `idle` names the ones made or used before but not in the last 10 minutes; with `items`, only those in the order given, 0 for one never made, and no `idle`. `rejected` for a name that is no item or fluid. |
| `map` | `{"resource"}`, optional | `{"position", "patches": [{"name", "tiles", "amount", "nearest", "distance", "center", "area": {"left_top", "right_bottom"}}]}`: resource patches and water (`name` `water`, no `amount`) in explored chunks, nearest first. Tiles in touching chunks count as one patch. Explored chunks are freeplay's starting area (200 tiles around spawn) and the 5x5 chunks around every chunk the agent has entered. With `resource` (`iron-ore`, `water`, ...), only that one's patches, and the nearest also has `rows`, its shape as the map view draws it: `[{"y", "x": [[from, to], ...]}]`, one entry per row of tiles, top first, each with the runs of neighbouring tiles that hold it. `rejected` when the explored map has none. |
| `walk` | `{"x", "y", "within"}`; `within` 0 to 10, default 1; the target at most 500 tiles away | The job. The route comes from the game's pathfinder; the job is `done` once the body is within `within` tiles of the target or at the end of the route, which counts as reached when the body is within half a tile of it and gets no nearer for half a second (the pathfinder can end a route on a point the body can't quite stand on, beside a rock). It fails with `no path` when nothing walkable reaches the target or the pathfinder gives no route in 10 seconds, and with `stuck` and the distance left to the target after 2 seconds without getting nearer the next point of its route, walking in circles included (decision 57). The `no path` error says why as near as the mod can tell, from the tiles the pathfinder routes through (those where the character fits standing at the centre, joined side to side, or corner to corner past two obstacles where it fits at the corner point): the agent is enclosed (with the tiles of room it has and the obstacle nearest the target that it can mine, or the nearest one when it can mine none), or, for a target on the explored map, the target is in a building or water or the target is enclosed (with the obstacle nearest the agent). |
| `mine` | `{"x", "y", "count"}`; `count` 1 to 1000, default 1 | The job. Mines what the agent would select at that point. Resources, trees and rocks must be within `reach.mine` of their collision box; fish, the agent's own buildings and items on the ground within `reach.interact` of their bounding box, else `rejected` (a point too far away for either is rejected without saying what is there). A fish gives 5 `raw-fish` after 0.8 s. A mined building comes back to the inventory with everything it held. Fluids such as crude oil can't be mined by hand; mining `crude-oil` says to place a pumpjack on the well, which pumps into a pipe (decision 66). Resources stop after `count` units, everything else when it is gone; a full inventory fails the job. |
| `craft` | `{"recipe", "count"}`; `count` 1 to 1000, default 1 | The job. The ingredients leave the inventory at once, and `used` lists them (decision 60). `rejected` when the recipe is unknown, locked (the message names the technology that unlocks it, and for a technology that unlocks by an action, that action; decision 66), needs a machine, or there are not enough ingredients for `count` crafts (intermediates included). |
| `job` | `{"id"}` | The job. |
| `jobs` | none | `{"running": [jobs]}` |
| `cancel` | `{"id"}` | The cancelled walk, mine or place_line job. Crafts can't be cancelled. |
| `place` | `{"item", "x", "y", "direction", "belt_type"}`; `direction` `north` (default), `east`, `south` or `west`; `belt_type` `input` (default) or `output`, for underground belts only | The placed building, as `inspect` shows it but without `distance`, plus `enclosed` when it closed the room the agent stands in and `warnings` when its output would land on the ground, have nowhere to go, or land on a belt lane that already carries something else, or an inserter has nothing to take from. A transport belt, or an underground belt's exit, also shows what it does to the belt it points into (decision 73): `continues` `{"name", "position"}` for one facing the same way, whose lanes go on on the same sides; `curves` `{"name", "position"}` for a transport belt with nothing behind it, which the new belt turned into a curve carrying both lanes on; or `sideloads` `{"name", "position", "lane", "blocked_lane"}`, where both its lanes go onto that belt's `lane` on the side it comes from, and for an underground belt `blocked_lane` is the lane of its own that the tunnel half blocks. Instant. The position snaps to the tile grid as the cursor does. An underground belt is the entrance (`input`) or the exit (`output`) of a pair; both ends take the direction items travel, and the exit goes further along that way (at most 4 tiles between the ends for `underground-belt`). `rejected` when the name is a fluid (decision 66), the agent has none of the item, it isn't a building, its nearest edge would be more than `reach.build` away, or the game's manual build check fails (overlap, including with the agent; water; a mining drill with nothing to mine under it; an offshore pump not on the shore facing the water), with the reason. `belt_type` on anything but an underground belt is `bad_request`. When the same building of the agent's already stands at that position facing that way (for an underground belt, as the same end), the result is that building with `already_there: true` and nothing is used up; facing another way, it is `rejected` with a hint to rotate it (or, for an underground belt, to mine and place it again). `enclosed` (decision 61) says, as `you are enclosed: no walkable route leaves your position now (about 7 tiles of room); mine this small-electric-pole, or another building around you, to get out`, that the room `walk` would explain a missing route with (the tiles the pathfinder routes through) has no way out now, and the new building is one of its walls. A room that reaches 1600 tiles or unexplored map counts as open. A machine placed on an electric network whose generators offered energy in the network's last update shows the `status` it has once its first electric update has filled its energy buffer, not the `no_power` the engine gives until then; where the generators offered nothing, `no_power` is real and stays. A mining drill over a mix of ore that needs a fluid (uranium ore needs sulfuric acid) and ore that doesn't also keeps the engine's `no_power`, since which one it mines first isn't known before it runs (decision 70). `warnings` is a list of sentences: `its output lands on the ground at X, Y: no belt or building is there to take it` for a drill or inserter showing `drops_at` on clear ground, `its output has nowhere to go at X, Y: the NAME there takes no items and leaves no room on the ground, so it stops without dropping any` for one showing `drops_at` on a building that takes no items, such as a pole or a drill (decision 70), `it has nothing to take from at X, Y: no belt or building is there` for an inserter showing `picks_at`, and, where what a drill or inserter drops is known before it runs (the item products of the resources in a drill's mining area, the products of the recipe of the crafter an inserter takes from, the items in the chest it takes from), `it drops ITEM onto the LANE lane of the NAME at X, Y, which already carries OTHER: a lane moves in single file, so an item that no machine along it takes stops at the belt's end and holds up the lane behind it` when that lane, on that belt or any belt joined to it with lanes kept (end on, round a curve, through an underground pair; not past a sideload or a splitter) within 32 tiles of the agent, the most `inspect` sees (decision 36), carries an item it doesn't drop, or `it mines A and B here and drops them all onto ...` for a drill over more than one resource (decision 73). It is left out when none applies. |
| `place_line` | `{"item", "x", "y", "to_x", "to_y", "direction", "spacing"}`; `direction` as for `place`, default the way the line runs from `x, y` to `to_x, to_y` (north for a single tile); `spacing` 1 to 64 tiles from one building to the next, default the building's length along the line | The job. Places a straight line of a building from the first end to the second, as a player drags it while running (decision 52). Both ends snap as `place` snaps them and must then share x or y; the line is at most 500 tiles long. With a spacing that doesn't divide the length, the last gap is shorter, so the line ends at the snapped `to_x, to_y` end, unless that gap is shorter than the building, which would overlap the one before: then the line ends one step short of it. Buildings go down in order, each as soon as it is in `reach.build`, one item each; the same building already there facing the same way counts as `already_there`. The body walks a lane 1.5 tiles beside the line, on the side it starts on, along a route from the pathfinder, to beside the last building, and keeps walking after the last one is down: the job is `done` when the body stands within 1 tile of the lane's far end. If that walk stops (`stuck`, `no path`) after every building is down, the job is still `done` and `stopped_short` says why and how far the body is from the last building, as `stuck: no progress for 2 seconds; you are 6.2 tiles from the last one`. Before then it fails where it stops, with the reason and `placed N of M; the next goes at X, Y`: `you ran out of <item>`, the build check's reason (`blocked by tree-01 at ...`), `stuck`, `no path`, or `the walk beside the line ended out of build reach of the next one`. `rejected` at once when the name is a fluid (decision 66), the first one is out of `reach.build`, the agent has none of the item, or the item is an underground belt; ends not in a straight line are `bad_request`. |
| `insert` | `{"x", "y", "item", "count"}`; `count` default all the agent carries | `{"inserted", "short", "entity"}`. Instant. Into one of the agent's buildings within `reach.interact`; the game puts the item where it belongs (fuel slot, furnace input, chest, assembler input, module slots, a rocket silo's input or its rocket's payload) and `rejected` when the building can't take it, or when the name is a fluid (`petroleum-gas`, `crude-oil`, `water`), which moves through pipes rather than by hand (decision 66). Asking for more than the agent carries hands over what it has, as a ctrl-click does, and `short` says how many it was missing (left out when it had enough); carrying none is `rejected`. `inserted` can be less than asked when the building fills up. Modules go only where the machine and its recipe allow all their effects; the rejection says which effect is refused, or that the module slots are full or missing. A rocket silo takes its payload (`raw-fish`, `satellite`) while the rocket is still being built. The gun and armor the agent has equipped stay on it and don't count as carried. |
| `take` | `{"x", "y", "item", "count"}`; `item` and `count` optional | `{"taken": [{"name", "count"}], "inventory_full", "entity"}`. Instant. With no `item`, takes everything in the building's output inventories (`chest`, `crafter_output`, `burnt_result`); with one, that item from any inventory. On a transport belt, underground belt or splitter it picks up what lies on that building's lanes instead, everything or the one item (decision 62). `count` caps the total. `rejected` when the name is a fluid (decision 66), and when there is nothing to take; the message then says what the machine is doing: what it is making and in about how many ticks the next one is done, or its status (`no_fuel`, `no_ingredients`, ...), and for a machine short of ingredients which ones, as `its status is item_ingredient_shortage: it is short of sulfur (has 0, one craft takes 1)` (decision 69). For a belt it says the belt has nothing, or none of the item, on it. |
| `rotate` | `{"x", "y"}` | The building, as `inspect` shows it but without `distance`, turned a quarter clockwise. An underground belt turns around instead, as in the game: an entrance becomes an exit facing the opposite way, and an exit an entrance; one end of a joined pair turns the other with it. A belt shows `continues`, `curves` or `sideloads` for the belt it now points into, as `place` does. `rejected` when it can't turn. |
| `inspect` | `{"x", "y"}` within 32 tiles | `{"name", "type", "position", "distance", "direction", "status", "inventories": [{"name", "slots", "items"}], "recipe", "progress", "missing": [{"name", "have", "need"}], "rates": {"crafts_per_s", "ingredients": [{"name", "per_s"}], "products": [{"name", "per_s"}]}, "burning", "mining", "drops_into": {"name", "position", "lane"}, "drops_at", "picks_from": {"name", "position", "lane"}, "picks_at", "fluids": [{"name", "amount"}], "pipes_to": [{"name", "position"}], "ports": [{"flow", "fluid", "pipe_at", "joined_to": {"name", "position", "fluid"}, "problem"}], "amount", "item", "rocket": {"status", "parts", "parts_required", "payload": [{"name", "count"}]}, "underground", "paired_with": {"name", "position"}, "lanes": {"left": [{"name", "count"}], "right": [{"name", "count"}]}, "turns", "capacity_per_s", "power": {"demand_kw", "capacity_kw", "satisfaction"}}`; fields that don't apply to the entity are left out. `status` is the game's entity status (`working`, `no_fuel`, `no_power`, `no_input_fluid`, `no_ingredients`, `waiting_for_space_in_destination`, ...), except that a machine connected to no generator, because it is in no pole's supply area or its poles have no generator, shows `not_plugged_in_electric_network` where the game says `no_power`, as the plug icon over it shows a player; `no_power` then means its network's generators can't run it (decision 59). An assembler, furnace or rocket silo whose status is `no_ingredients`, `item_ingredient_shortage` or `fluid_ingredient_shortage` shows `missing`: each ingredient of its recipe (for an idle furnace, the one it last smelted) it holds less of than one craft takes, `have` what it holds and `need` what one craft takes, fluids included (decision 69). `rates` is per second at full power (decision 71): a crafting machine with a recipe gives `crafts_per_s` at its crafting speed, modules and beacons included, with the `ingredients` it uses and the `products` it makes, productivity included; a mining drill gives the `products` of the resource it mines, or before it runs the first under it that it can mine, from its mining speed with its speed bonus over the resource's mining time, times its productivity bonus (mining research included), and none for a fluid such as crude oil. A drill or inserter shows `drops_into` the building its output goes into (a belt, an assembler, furnace or rocket silo, with or without a recipe, or one of the agent's buildings with an inventory, whose selection box holds the drop point), whether or not it is running yet, or else `drops_at`, the drop point, where no building takes its output (decision 54): on clear ground the output lands there; a building without an inventory, such as an electric pole, or with module slots only, such as a mining drill or a beacon, doesn't take it and leaves no room on the ground, so the drill or inserter drops nothing and stops (decision 70). A pumpjack, whose crude oil leaves through its pipes, shows neither. An inserter likewise shows `picks_from` the belt or building at its pickup point, or `picks_at` the point when nothing is there. When `drops_into` is a transport belt, underground belt or splitter, its `lane` (`left` or `right`, facing the way items travel) is the lane the items land on, and `picks_from` on one gives the `lane` the inserter takes from first; it takes from the other lane when that one has nothing its target accepts. The lanes follow rules probed on 2.1.24 for every orientation (decision 73): on a straight belt, underground belt or splitter, the lane on the side of the belt's centre line the drop point lies on, the right lane when it lies on the line (an inserter fills the far lane of a belt crossing in front of it, a drill the near lane; a belt running along an inserter's arm or a drill's facing gets the right lane, except that a burner drill fills the left lane of one running toward it); on a curve an inserter fills the lane farther from it, and a drill beside an outer side the outer lane. An inserter takes the near lane of a crossing belt first and the left lane of one running along its arm; on a curve, the outer lane from beside it and the inner lane from either end of the curve (the end it leads to, or the end it comes in from, which a long-handed inserter reaches over the feeding belt). An entity with fluid boxes shows its `fluids` and the entities its pipe connections join (`pipes_to`). A machine whose pipes have sides (an assembling machine, which a refinery and a chemical plant are, a pumpjack, a boiler, a steam engine) also shows `ports` (decision 80), one entry per pipe connection: `flow` is `input`, `output` or `input-output` (the fluid passes through, as water through a boiler), `fluid` the fluid its recipe puts there or that it holds (left out when neither is known), `pipe_at` the tile a pipe has to stand on to join it, and `joined_to` what is joined there now, left out when nothing is. The ports turn with the machine and follow its recipe. `amount` is what a resource tile has left; `item` names the item of an `item-on-ground`. A rocket silo shows `rocket`: `status` is the game's silo status (`building_rocket`, then the rocket rising through `doors_opening`, `rocket_rising` and `arms_advance` to `rocket_ready`, then `launch_starting` and on through `rocket_flying` to `doors_closing`), `parts` the rocket parts made toward the rocket being built (back to 0 once it stands in the silo), and `payload` what the rocket will carry. An underground belt shows which end it is, `underground` (`input` or `output`), and the other end of its pair, `paired_with`, once there is one. A transport belt, underground belt or splitter shows `lanes`: the items lying on its `left` and `right` lane, facing the way items travel (decision 62), a transport belt that is a curve shows `turns` (`left` or `right`, the side its inner lane is on), and `capacity_per_s`, the most items one belt of it moves per second with both lanes packed: 8 items a tile at its speed, 15 for `transport-belt` (decision 71); a splitter moves that on each of its two belts. An underground belt counts the part going under with its lanes, and a splitter adds up its two belts per side. An electric pole, and any machine on an electric network, shows `power`, what hovering a pole of that network shows (decision 55): `demand_kw`, what its machines ask for, `capacity_kw`, what its steam engines, turbines and solar panels can give (accumulators count only what they gave), and `satisfaction`, the share of the demand met from 0 to 1 (left out when nothing asks); below 1 the machines run slower and show `low_power`. Taken from the engine's last electric update. A machine in reach of no pole has no `power`. |
| `set_recipe` | `{"x", "y", "recipe"}` | `{"returned": [{"name", "count"}], "entity"}`. Instant. Sets what one of the agent's assembling machines within `reach.interact` makes. A chemical plant and an oil refinery are assembling machines, so the same call sets `plastic-bar`, `sulfur` or `basic-oil-processing`. Ingredients it held that the new recipe doesn't use come back to the inventory (spilled at the agent's feet if it is full). `rejected` for other buildings (the message names a chemical plant and an oil refinery as machines that do take a recipe), unknown or locked recipes (a locked one names its technology, as `craft` does; decision 66), and recipes the machine can't make (the message names the crafting category, such as `chemistry` or `oil-processing`). |
| `research` | `{"tech", "cancel", "show", "researched"}`, all optional | With no `tech`, the state: `{"current": {"name", "progress"}, "queue", "available": [{"name", "unlocks", "leads_to", "cost": {"units", "packs", "seconds_per_unit"}, "trigger"}], "researched"}`. `current` is left out when nothing is being researched; its `progress` runs from 0 to 1. `available` lists technologies whose prerequisites are researched or queued; each has a lab `cost` (`units` of `seconds_per_unit` each, every unit taking one of each science pack in `packs`) or, for the ones that unlock when the force crafts, makes or mines something, a `trigger` in words (`craft 1 lab`, `make 10 copper-plate in a machine (smelting)`, `extract crude-oil with a pumpjack`), and `leads_to` names the technologies that have it as a prerequisite. `researched` is how many technologies are researched; with `researched: true` the result also has `researched_names`. With `tech`, queues every prerequisite, all the way back, that is neither researched nor queued, each after its own prerequisites (the `needs` order), then the technology, as clicking it on the tech screen does, and returns `{"current", "queue"}`; with `cancel: true`, takes it out, along with whatever was queued behind it as a prerequisite, and returns the same. With `show: true`, returns the technology without touching the queue, as the tech tree screen shows it: `{"name", "state", "unlocks", "leads_to", "cost", "trigger", "prerequisites", "needs"}`, where `state` is `researched`, `current`, `queued`, `available` or `locked` and `needs` lists every prerequisite, all the way back, that is neither researched nor queued, each after its own prerequisites; it can include technologies that unlock by an action rather than labs, and `show` on one of those gives its `trigger`. `rejected` for unknown technologies (with `show` too); with `cancel`, for one not in the queue; and when queueing, for trigger technologies, a prerequisite still to do that unlocks by an action (naming it and its trigger), researched ones, ones already in the queue, a queue without room for the technology and its missing prerequisites (it holds at most 7 technologies, the current one included; the message gives the slots needed and the technologies), and a technology the engine's queue won't take. A rejection queues nothing. |
| `launch` | `{"x", "y"}` | `{"launched": [{"name", "count"}], "entity"}`. Instant. Launches the rocket from one of the agent's rocket silos within `reach.interact`, as the silo's Launch button does. `rejected` when it isn't a rocket silo, the rocket isn't built yet (the message gives the parts, such as 37/100), it is still rising into launch position, a launch is already under way, or the rocket has no payload (the game's button doesn't launch an empty rocket). The game counts the launch when the rocket reaches space, about 19 s later. |
| `screen` | `{"zoom", "grid"}`: zoom 0.5 to 3, default 1; `grid` true or false, default true | `{"tick", "width", "height", "zoom", "center", "area": {"left_top", "right_bottom"}, "grid_tiles", "png_base64"}`: what the agent's screen shows (decision 67), rendered by the camera client on `tick`. 1920x1080 pixels centred on the body (`center`), at 32 pixels per tile at zoom 1, so `area` is the map tiles it covers (60 by 33.75 at zoom 1); alt mode on, warning icons drawn (unplugged, no power, no fuel), no GUI panels, lit by the surface's own daytime. With `grid`, map coordinates lie over it (decision 78): a thin line along the tile edges every `grid_tiles` tiles (10, or 5 at a zoom above 1.5) and `x,y` at each crossing; without, there is no `grid_tiles`. `png_base64` is the PNG in base64, several megabytes; `fac screenshot` writes it to a file and prints the rest with that file's `path`. Pipes and replacing (decision 83). In `ports`, `joined_to.fluid` is what the pipe, pipe-to-ground, storage tank or pump joined there holds, and `problem` says so when that is not the port's `fluid`. A pipe-to-ground shows `paired_with`, the position of the other end of its underground run, in every result that shows it; `place` on one with no partner says so in `warnings`, and `place_line` is `rejected` for it as for underground belts. `place` on a building of the same kind and size that the game lets a player replace in place (an assembling machine for a faster one, a stone furnace for a steel one, a belt for a faster belt) swaps them: the new one keeps the recipe and contents, the old one goes to the inventory, and the result names it in `replaced`.

|---|---|---|

## Daemon to mod

Internal to the daemon, documented here because the mod must match. The daemon sends `/factobot <method> <params as JSON>` (agent and harness methods) or `/factobot-dev <lua>` (the `lua` dev method) over RCON. The mod prints one JSON line, `{"ok": true, "result": ..., "tick": N}` or `{"ok": false, "error": "<message>", "code": "<code>", "tick": N}`, and refuses calls from players. A line that answers an agent method also has `hud`, which the daemon passes on as the response's `hud`. `code` is `rejected`, `bad_request` or `unavailable` when the caller or the world state caused the error, and absent for mod bugs, which the daemon reports as `game_error`. Lua writes an empty list as `{}`, so the daemon turns every empty object in an agent result or the dev `milestones` result into `[]`. Lua can't write a null either, so the daemon adds `rocket_launched_tick: null` to the `milestones` result when the mod leaves it out. Both the dev `screenshot` and the agent's `screen` render through the mod's `screenshot` method (`{"player", "path", "width", "height", "zoom", "x", "y", "daytime", "grid"}`, centred on the body when `x` and `y` are left out, with a coordinate grid every `grid` tiles when that is given, returning `{"center"}`); the daemon then waits for the camera to write the file. No socket passes `screenshot` to the mod as it is.
