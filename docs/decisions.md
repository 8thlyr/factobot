# Architecture decisions

Decided 2026-11-01. Background is in `research.md`.

| # | Topic | Decision | Notes |
|---|---|---|---|
| 1 | Base | Fresh build | Our own mod, daemon and CLI. Borrow patterns from FLE's Lua (MIT) and autorio's design: real walking and harness-observed scoring. |
| 2 | Timing | Real-time, game speed 1 | The game runs continuously, so thinking time costs game time. Actions are async: commands start walking, mining or crafting and return a job ID, and the agent can poll or wait on it. Results record game ticks and wall-clock time separately; the model's speed is part of the score. Changed from turn-based on 2026-11-01: pausing made thinking free and time unrealistic. |
| 3 | Actions | Player-like | Real walking (`walking_state` along pathfinder routes), reach limits, real mining and craft times, fog of war. No auto-routing helpers: the agent places belts itself, tile by tile or by blueprint. |
| 4 | Vision | Both, as tracks | A synthetic top-down render is the cheap default. Real screenshots come from an Xvfb spectator client (`take_screenshot{by_player=...}`). Text state is always available. |
| 5 | Menus | API stand-ins first | The first release exposes craft, research and set-recipe as commands, with structured state that resembles the menus. Phase 2: evaluate czp3009/factorio-mcp injection as a separate real-UI track. |
| 6 | Host | Headless server + optional spectator | The free headless server is the source of truth. A graphical spectator joins only when the vision track is on. Text-only runs need no game license. |
| 7 | Interface | CLI first | `fac <verb>` commands that return JSON. An MCP wrapper over the same daemon API comes later. The agent's sandbox exposes only the CLI, not harness code or RCON. |
| 8 | Game | Factorio 2.1.24 (stable on 2026-11-01), base game only | Pinned with its checksums in `mise.toml`. Space Age, Quality and Elevated Rails are disabled in the generated `mod-list.json`. |
| 9 | Enemies | Peaceful, with no enemy bases, for the first release | Combat tasks come later. |
| 10 | Infra | Develop on a desktop, run evals on a server | The desktop has a display for watching the game. Game binaries are downloaded at runtime and never baked into images. |
| 11 | Language | Rust core + thin Python layer | One Rust binary holds the daemon (RCON, jobs, telemetry, process supervision, synthetic renderer, screenshots), the `fac` CLI and the MCP server. A Python package contains the Inspect AI tasks, scorers and leaderboard tools, and acts as a plain client of the daemon's versioned JSON socket API (no PyO3). The mod stays Lua. MCP via `rmcp` (official SDK, spec 2026-07-28). FLE's Python renderer (MIT) is the reference for a Rust port. autorio, czp3009/factorio-mcp and factorioctl have no license, so we take ideas from them only. |
| 12 | RCON client | Our own, about 150 lines in `crates/factobot/src/rcon.rs` | The `factorio-rcon` crate (0.1.0, 224 downloads) was too young to depend on. Probed on 2.1.24: Factorio answers each command with exactly one packet regardless of size (300 KB tested) and ignores the empty end-of-response marker, so responses are matched by packet id. |
| 13 | Agent-facing interface | Binary `fac`, crate `factobot` | Every command prints one JSON object. The daemon calls the mod through the `/factobot` console command, never `/c` or `/sc` (those disable achievements and need a repeated first call). |
| 14 | Repo, CI and license | `8thlyr/factobot`, public since 2026-11-12 (private before that); CI on the repo's self-hosted runner; MIT OR Apache-2.0 | The runner (label `factobot`) runs as its own user. A pull request from a fork runs on a GitHub-hosted runner, never the self-hosted one, and its workflows wait for a maintainer's approval (a repository setting, since a fork can edit `ci.yml`). The public repo starts from a fresh history. |
| 15 | Launch scope | Leaderboard of current frontier models, flagship rocket-run video, technical report, live viewer website | Eval API budget $500-2,000. |
| 25 | Harness debug channel | A second daemon socket (`dev.sock`) with `lua`, `world_hash`, `snapshot` and `reload`; agents only get the agent socket | Developers and tests need to read and set any game state; agents must not. Agent sandboxes mount the agent socket file alone, since the default puts `dev.sock` beside it. `reload` restarts the server from its save because `game.reload_mods()` does nothing in multiplayer, and the headless server is multiplayer. The daemon exits non-zero if the server dies outside a restart. |
| 26 | Mod type checking | lua-language-server checks the mod against types generated from Factorio's own API docs by FMTK 2.1.9 | API misuse fails lint before it reaches the game. FMTK is the standard Factorio mod toolkit (justarandomgeek); it has few npm downloads because most people install it as a VS Code extension. |
| 27 | Freeplay start | The mod turns off freeplay's crash site wreck and intro, and charts freeplay's starting area itself when the map is created | Freeplay builds the wreck and charts the start when the first player is created, so the world depended on whether a camera, viewer or agent joined first; a live test caught the world hash changing. The wreck's items still go to the player's inventory, so the starting resources are the same. |
| 28 | Watching and screenshots | Graphical spectator clients: a camera on a private Xvfb (Mesa llvmpipe) for screenshots, and a viewer window for people; the mod removes the body of every player | The headless server can't render. Spectators without characters keep the world unchanged, which a live test checks with the world hash. They connect over the game port with user verification off, so no account token goes near them. |
| 29 | Agent playtests | Claude Code headless, restricted to `fac` commands, in an empty workspace with no host settings, CLAUDE.md, skills or MCP; the agent's `fac` refuses harness subcommands | Finds usability problems in commands before the benchmark. It is a development check; the benchmark itself will need a real sandbox. Replaced by decision 46: the runner takes any harness, and a bubblewrap sandbox, not Claude Code's permission rules, limits it to `fac`. |
| 30 | Agent body | A `character` entity the mod creates when the map is created, with no player attached, at the spawn point with freeplay's starting items | The headless server has no player to use. Probed on 2.1.24: a playerless character walks at the normal 0.15 tiles/tick through `walking_state`, mines through `mining_state` at the character's 0.5 mining speed and `resource_reach_distance` 2.7, and hand-crafts through `begin_crafting` with intermediates queued automatically, so the engine enforces speeds, reach and craft times. FLE uses the same kind of body but teleports and inserts items instantly in its default mode. |
| 31 | Fog of war | The mod keeps the set of explored chunks: freeplay's starting area, plus the 5x5 chunks around every chunk the agent enters, which it also generates. Map queries see only explored chunks | A player's character reveals 5x5 chunks around it, but a playerless character reveals nothing, and the headless server builds no chart at all without a connected client (probed: `force.chart` and `chart_all` leave `is_chunk_charted` false). The mod still calls `force.chart` so a viewer sees the same area. |
| 32 | Jobs | `walk`, `mine` and `craft` return a job at once and run in game time. Walking and mining use the body, so starting one cancels the other; crafting runs in the hand-craft queue alongside them, first in first out | Decision 2 made actions asynchronous. A player can't walk and mine at once but can craft while doing either. `fac job ID --wait` and `--wait` on each action block in real time; nothing pauses the game while an agent waits. |
| 33 | Walking | The pathfinder plans a route from `surface.request_path` with the character's collision box and mask; the mod steers along it in the eight directions a player can walk, one direction change per tick | Same movement a player has, without the agent steering tick by tick over RCON. A route that stops making progress for 2 seconds fails as `stuck` (decision 57). |
| 34 | Rejections | An action the game rules forbid (out of reach, recipe locked, missing ingredients, nothing to mine) fails at once with error code `rejected` and a message that says why | Agents learn the rules from the errors, so the message names the limit, for example the reach distance and how far away the target is. |
| 35 | Building | `place` puts a building from the inventory onto the map at once, snapped to the tile grid as the cursor snaps it. It must pass the game's manual build check (`can_place_entity` with `build_check_type.manual`) and lie within `build_distance` (10), measured from the character to the nearest point of the building's collision box | A player places instantly. A playerless character has no cursor, and `LuaPlayer.can_place_entity` needs a player, so the mod measures build reach itself the way the engine measures interaction reach (probed: `can_reach_entity` and the engine's mining of buildings both stop at 10 tiles to the box edge). The manual check rejects overlaps (the agent included), water, and drills with nothing to mine (probed). |
| 36 | Using machines | `insert`, `take` and `rotate` act at once on the agent's own buildings within `reach_distance` (10), using the engine's `can_reach_entity`. `insert` uses the game's routing (fuel to the fuel slot, ore to the furnace input), so a machine only takes what it can use; `take` with no item empties the output inventories. `insert` hands over only what the agent carries, not the gun and armor it has equipped. `inspect` shows any entity within 32 tiles: inventories, status, recipe, fuel, where a drill's output goes, and the fluids in it with the entities its pipe connections join | Same instant transfers a player makes with ctrl-click. `insert` takes from the main inventory plus the ammo and trash slots, and leaves the gun and armor slots in place. Counting equipped items as carried let `insert` copy a pistol or worn armor, since the engine's `remove_item` never takes from those slots (found in review). Telling the agent where a drill drops its output, and what it drops into, is what a player sees from the drill's arrow. |
| 37 | Picking up | `mine` also takes the agent's own buildings, with what they hold, and items on the ground, within `reach_distance` of their box, in game time | A player picks up a building or a dropped item by mining it. The engine does the mining; it mines the character's selected entity, so the mod restores the selection after looking at other entities (found when an `insert` during a mine job made the character mine the furnace instead). |
| 38 | Remote watching | `fac daemon --listen <address>` moves the game port off localhost, and `fac watch HOST` joins from another machine as a spectator. Every player is a spectator whatever its name, in the `factobot-spectators` permission group, which denies every input action except moving the view, remote view, changing the surface the view is on, toggling entity info and opening read-only windows (production, bonuses, achievements, trains, logistics, electric network); RCON stays on localhost | Worlds run on the server (decision 10) while the person watching sits at the desktop. A joining client simulates the game itself and draws it on its own GPU, which looks far better than streaming a screen. With user verification off a client can claim any name, so the mod no longer trusts the `factobot-*` prefix and removes every player's body. A bodiless spectator could still queue research for the agent's force from the technology screen (seen in a probe: the force then researched it), chat, run console commands and change entity settings, so the group is an allow-list: actions added in a later game version start denied. Chat is denied too, since the agent must not get help from a watcher. The agent has no player and the daemon talks over RCON, so the group never limits either. Listen only on a private network such as the tailnet: anyone who reaches the port can watch the whole map. |
| 39 | Hand-craft statistics | When the agent's hand-crafts finish, the mod adds their products (intermediates included) to the force's item production statistics with `on_flow` | The engine counts a player's hand-crafts in production statistics, and craft-item research triggers fire from those counts. It counts nothing a playerless character crafts (probed on 2.1.24), so without this a hand-crafted lab would never unlock red science and the agent could never research. `on_flow` fires the trigger as a player's craft does, including for a lab crafted before the technology became available (probed with a connected player). Hand-mining is already counted. |
| 40 | Research | `research` adds a technology to the end of the force's research queue, as clicking it does, and shows the current research, the queue, and what is available with its lab cost or its trigger in words. The engine runs research in labs | Labs need power and science packs, the same as for a player. Technologies unlocked by a trigger (make 50 iron plates, craft a lab) can't be queued; the rejection says what unlocks them. A craft-item trigger counts the force's production, so for an item no hand recipe makes it says "make 50 iron-plate in a machine (smelting)": "craft" sent agents to `fac craft`, which rejects smelting recipes (review round 1 of PR 57). A technology queues behind its queued prerequisites, as the engine allows (probed), so the agent can plan several steps ahead. `fac research --cancel` takes a technology out of the queue, and the engine drops with it the technologies queued behind it that depended on it (probed). |
| 41 | Assembler recipes | `set_recipe` sets the recipe of one of the agent's assembling machines within `reach_distance` after the mod checks the recipe is unlocked and the machine's crafting categories include it; ingredients the new recipe doesn't use come back to the inventory, and any that don't fit are spilled at the agent's feet | A player picks the recipe in the machine's window. `LuaEntity.set_recipe` accepts a recipe the machine can't make without an error and leaves it with no recipe (probed), so the check is the mod's. |
| 42 | Water and offshore pumps | `observe` lists water tiles among the resources and `map` reports water patches, both without an amount. Placing an offshore pump where it doesn't fit is rejected with the nearest tile and direction within 4 tiles where it passes the build check and is in build reach | Water is where an offshore pump goes, so the agent needs to find it like ore. A player sees the shore and the pump's ghost turn green; the agent has no cursor, so the rejection tells it where the pump fits. |
| 43 | Observing the milestone | The mod counts the science packs the agent hand-crafts, takes machine-made packs as the force's production statistics minus those, and records per pack the first tick on which labs have used up more packs than were ever hand-crafted, plus machine-made packs so far at the end of every game minute. The harness reads them on the dev socket (`milestones`); agents can't | Decision 18 stops the clock when labs research with a machine-made pack, but a pack carries no record of where it was made. Labs' use shows in the force's consumption statistics as each pack is started (probed), and using more packs than were hand-crafted proves one came from a machine, so hand-crafted packs alone never stop the clock. The per-minute series lets the harness check decision 18's sustained throughput for any N later. Packs a script puts into the world (a test, or a starting save's chests) aren't in the production statistics, so labs using them stop the clock as a machine-made pack would, though they never appear in the machine-made counts; starting saves for later stages will need a baseline. A save from before mod 0.4.0 counts every pack made before the upgrade as hand-made. |
| 44 | Inspect AI tasks | `inspect eval factobot/red_science` runs ladder stage 1 (decision 22) on seeds 1 to 5, one fresh world each. The model gets Inspect's ReAct agent with one tool, `fac`, no submit tool and summary compaction. The clock starts when the agent gets its first prompt; the run ends when the stage counts (the harness sees the milestone, decision 43, and with a throughput gate machines have sustained N), once the game-time cap has passed, or at Inspect's own limits. The score is decision 23's, from decision 21's 5 h and decision 20's 2x cap, reported as the median over seeds and the standard error of the mean | ReAct works with every provider Inspect supports, where Claude Code (decision 29) is one vendor's agent. One tool and no shell keeps decision 7's "only the CLI" without a container: the tool runs `fac` without a shell, with the agent socket alone, and refuses `dev`, `daemon`, `watch`, `--socket` and `--dev-socket`, so an agent can't reach another sample's world or the dev socket. The world runs while it boots (servers start unpaused); the harness then pauses it, reads the start tick, and unpauses it as the agent's first turn begins, so boot time isn't the agent's. The cap is checked between model turns. Decision 18's N is a task parameter (`-T throughput=N`) with no default while it is still open; with it, the prompt states the rate and the stage counts once machines average N packs a minute over 10 whole game minutes after the milestone; without it the stage counts at the milestone. A sample whose world never starts is an error, not a score. Each world gets a thread of its own because the harness stops a world when the thread that started it ends. Not yet: the dollar cap, and stages 2 to 5, which need starting saves. Shelved, not removed (decision 46): the code and tests stay, but the benchmark is now any harness playing through `fac`. |
| 45 | Outage pauses | Inspect's `on_model_retry` hook pauses the sample's world before each retry of a failed model call, and its `on_model_usage` hook resumes the world when a call succeeds (failing that, the harness resumes it when the agent's `fac` tool or the end of its turn runs). Benchmark runs turn off the provider SDK's own retries: `-M max_retries=0` for the `anthropic` and `openai` providers, `-M disable_retry=true` for xAI's; Google's SDK client has no such switch. The paused seconds and the number of outages go into the score's metadata; with `-T pause_cap=S`, a run paused longer than S seconds is void, an error rather than a score. The task sets `fail_on_error=False`, so a void or broken seed leaves the other seeds running and the metrics cover the seeds that scored | Decision 19's way to keep outages from costing the agent game time. ReAct calls the model inside Inspect, so Inspect's own retry loop is the proxy decision 19 expected to need, and the hooks name the sample's world through a context variable. Provider SDKs (Anthropic's and OpenAI's retry twice by default) retry some failures inside one call where no hook sees them, which would run in game time, hence `max_retries=0`. The first failed attempt runs in game time and the call that ends an outage runs paused; every other call, however slow, runs in game time. The cap is still open, so it has no default and no run is void without it. Inspect's default ends the whole eval at the first sample error, which would throw away hours of the other seeds' play over one seed's outages; `--fail-on-error 1` restores it. Shelved with decision 44 (decision 46). |
| 46 | Any agent harness | The benchmark is the world plus the `fac` CLI, and any agent harness plays it as it ships; scores compare harness and model pairs (Claude Code with Opus, omp with another model). `python -m factobot.playtest` runs a preset (`--agent claude`, `--agent omp`) or any command after `--`, with `{prompt}` replaced by the prompt, in a bubblewrap sandbox: the harness sees the agent's `fac` (decision 64), the agent socket, its own binary, a throwaway home with a copy of its login, read-only `/usr` and `/etc`, and the internet through a network namespace of its own (slirp4netns with `--disable-host-loopback`, and unreachable routes for the host's own addresses and the private, tailnet and link-local ranges); not the repo or worktrees, the run directory, the dev socket, the host's `/tmp`, `/run/user` or the rest of `$HOME`, other processes (`--unshare-pid`), the host's abstract Unix sockets, its localhost, nor its LAN and tailnet, where `--listen` puts the game port. The one exception is omp's auth broker: the sandbox may reach its IPv4 address on its TCP port only, held there by nftables rules in the sandbox's namespace. Every harness gets its own shell inside, Claude Code included. Turns and cost come from the harness's own report when it gives one (Claude Code) and are null otherwise. The Inspect AI path (decisions 19, 44, 45) is shelved, not removed: its code and tests stay | Decided by JC on 2026-11-02. A harness (its tools, context handling, retries and prompting) shapes how well a model plays as much as the model does, and people want to know how the agents they use do; Inspect's ReAct loop measures models inside one generic harness only. Running harnesses as they ship means the sandbox has to come from the OS: each harness has its own permission rules, and none should be trusted to hold itself. bubblewrap needs no root or container runtime and starts in milliseconds. Sharing the host's network namespace would hand the agent every abstract Unix socket on the host (an X server's among them) and every localhost service, so the sandbox gets its own, and slirp4netns, also rootless, gives it outbound internet only. One sandbox for every harness means a difference in score comes from the harness and model, not from what each was allowed, which is why Claude Code no longer runs with only `Bash(fac:*)` allowed while omp has a full shell. The agent can read its harness's login, since the harness runs as the agent; Claude Code gets a copy of its Claude.ai login only, and a login it refreshes during a run goes back to the host in case the refresh retires the host's copy; omp gets the auth broker's URL and token, the smallest setup that works with JC's broker. Turns and cost are left null rather than estimated where a harness does not report them. The broker runs on the host's own tailnet address, which the walls around the host's networks would otherwise block, and omp cannot log in without it; routes can't tell ports apart, so nftables keeps the rest of that address, a game port among them, out of reach. Still open: outage pauses (decision 19) when the harness calls its model itself, the dollar cap, and the login write-back. That last one was written down on 2026-11-11 (PR 70), after the decision above and not as part of it: the agent could hand back another account's tokens the same way, since nothing in the file names the account, and the host's Claude Code, outside the sandbox, would then run as that account and load its claude.ai connectors, the plugins turned on for it on claude.ai by its owner or its organization, and its Team or Enterprise organization's managed settings, hooks among the last two. That is a way out of the sandbox which holding the host's refresh token does not give, and the one known gap in the AGENTS.md "Agent sandbox" invariant. The write-back stays for now so that a long run does not leave the host logged out, and `docs/development.md` says why no lookup of the account settles it after a run and to log the host in again instead; whether to keep it at that cost is JC's to decide. |
| 47 | Stopping a world | Only the daemon stops its server. On SIGINT, SIGTERM or SIGHUP it sends RCON `/quit`, which saves `save.zip`, and waits up to 60 s before it kills the server. The server runs in its own process group with SIGTERM blocked, and dies with the daemon if the daemon is killed outright. The harness gives the daemon 90 s; a playtest runner on SIGTERM, SIGHUP or a first Ctrl-C stops the agent, then the world, and a second Ctrl-C interrupts it. No periodic autosave: `autosave_interval` stays 0. The assisted speedrun track's runner saves on a timer anyway (decision 48), outside the daemon. | Factorio saves on its first SIGTERM or SIGINT and quits mid-save on a second, leaving the old `save.zip` and a partial `save.tmp.zip`. `systemctl stop` sends SIGTERM to every process of the unit, then again as soon as the main process exits; on 2026-11-03 the two reached a playtest's server 15 ms apart, and the world of a 3-hour run was lost. A double Ctrl-C did the same to a server in the terminal's process group. Factorio keeps a blocked SIGTERM blocked in every thread, and SIGINT still saves, for stopping a server by hand (probed on 2.1.24). The death signal is SIGKILL because a saving one can't work: the kernel sends it again as the server passes to each of the dying daemon's threads (probed: two SIGINTs, save lost). 60 s fits systemd's default TimeoutStopSec of 90 s. Autosave adds little: every stop path saves, and a crashed benchmark run is void anyway, since the harness can't restore the agent's context. Each save pauses the real-time game for as long as it takes (about 60 ms for a small world, more as the factory grows), thinking time the agent would get for free. `unsafe_code` is denied rather than forbidden so that `server.rs` can block the signal in `pre_exec`. A runner started in a terminal (`mise run speedrun`) is usually stopped with Ctrl-C, which reaches the runner and the agent's sandbox but not the daemon, in a session of its own; as an interrupt it would unwind the run without writing `summary.json`, so the first one is handled like SIGTERM. |
| 48 | Assisted speedrun track | `mise run speedrun` runs an agent from a fresh map (or a save) to a rocket launch with help given on purpose: a speedrun skill compiled from web research, including seed coordinates, copied into the sandbox home with `--skill`, and a prompt aimed at speed. The runner stops it at the first launch (`--until rocket`), resumes an agent that quits early in the same conversation (`--max-resumes`), and saves the world every 10 minutes of wall time with `game.server_save` (`--autosave-minutes`), rotating three files that `--save` continues from. Its times are not benchmark scores, and its results are reported apart from the ladder and the full run | Asked for by JC on 2026-11-03, to see how far an agent gets toward a rocket with as much help as we can give it. A skill tells the agent what to build and in what order, so a run with one measures the skill as much as the agent, and comparing it with unassisted runs would not be fair; keeping the track separate keeps the benchmark's scores clean. Resuming matters because a headless harness ends its turn when it thinks it is done or stuck, and a run to a rocket takes many hours; a short message in the same conversation keeps what the agent learned, where a fresh agent would have to look around again. Autosaves exist because a run that crashes can otherwise lose hours, and decision 47 saves only when a world stops; each save pauses the game briefly, which the benchmark avoids but an assisted run can afford. They are written by the runner, not the daemon, so they need no change to how worlds start; three names in turn mean a save cut short by a kill still leaves two good ones. |
| 49 | Finishing the game | `launch` launches the rocket from one of the agent's rocket silos within `reach_distance`, only when the rocket is built, standing ready and carrying a payload; `insert` loads the payload (`raw-fish` or a satellite), the rocket part ingredients and modules through the game's routing; `mine` takes fish with `reach_distance`; `place` takes `belt_type` for underground belts. The mod records the tick of the first `on_rocket_launched` as the rocket milestone (`rocket_launched_tick` in the dev `milestones`) | A player clicks Launch in the silo's window, which needs the silo in reach, and the button stays off while the rocket has no payload; `LuaEntity.launch_rocket` launches an empty rocket too (probed on 2.1.24), so the mod checks the payload itself. The game routes modules only into machines whose prototype and recipe allow all their effects, and a silo's payload into the rocket even while parts are still being made (probed), so `insert` needs no rules of its own. The engine mines a fish at interaction reach, to its bounding box, not at the shorter mining reach (probed). A player turns an underground belt before placing it; `create_entity` makes an entrance unless told otherwise (probed), so `place` says which end. The game counts a launch when the rocket reaches space, about 19 s after the launch order (probed: 1162 ticks, when `on_rocket_launched` fires), so that is the milestone tick. |
| 50 | Short answers from what a player sees | Results carry what a player sees at a glance and leave out what an agent re-reads for nothing. `observe` shows each machine's status (the icon over it) and each building's direction, folds a straight run of transport belts into one entry, and leaves out corpses, stumps and entity distances. `research` shows where each available technology leads and looks any technology up with `--show` (state, cost, prerequisites, every prerequisite still needed, what it leads to), as the tech tree screen does; queueing returns the queue alone, a full queue says the engine's cap of 7, and the researched technologies are a count unless asked for. `fac inventory` shows what the agent carries. Craft jobs carry `eta_tick`. A `take` that finds nothing says what the machine is making and when the next item is done, or its status. Placing the same building where it already stands, facing the same way, does nothing and says `already_there` | The 3-hour Claude Code playtest of 2026-11-03 spent 48% of its output bytes on observe and research, piped observe through grep 110 times for one inventory count, polled furnaces with 100 empty `take`s, re-placed things already there 56 times, and went for military science partly because research showed nothing past the next step. None of this gives the agent more than a player has: status icons, building directions and the tech tree are on screen, a machine's progress bar is one click away (and `take` needs the machine in reach, as opening its window does), and clicking a building onto the same building does nothing. On the run's end save at its 179 observe positions, observe entries take 37% fewer bytes per entity seen (61 against 97), and 125 calls instead of 48 see everything in their radius. |
| 51 | Why a walk has no route | When the pathfinder finds no route, the mod flood-fills the tiles it routes through (those where the character fits standing at the tile's centre, joined side to side, or corner to corner past two obstacles where the character fits at the corner point), from the agent and, when the target lies on the explored map, from the target, up to 1600 tiles each. A fill stops at the edge of the explored map and then says nothing about that room, so the error never names what stands on unexplored map. The error says whether the agent is enclosed (with the obstacle nearest the target that it can mine, or the nearest one when it can mine none), the target is in a building or water, or the target is enclosed (with the obstacle nearest the agent) | The pathfinder reports failure without a reason, and the playtest agent learned by trial that it "can get boxed in among machines". Probed on 2.1.24: the pathfinder won't route between two inserters, poles or furnaces standing side by side, though the character fits between them, so the fill uses tile centres to agree with it. It does step diagonally between two walls, poles, inserters or pipes that meet at a corner, though not between two iron chests, even though the character fits at the corner point. A player sees what stands around a target on the map view, which shows explored chunks only (decision 31). |
| 52 | Dragging a line | `place_line` (`fac place ITEM X,Y --to X2,Y2`) is a job: the first building must be in build reach, then the body walks a lane 1.5 tiles beside the straight line at running speed, along a pathfinder route, and each building goes down through the same checks as `place`, one item each, in order, as soon as it is in build reach. ## Goal

A public release meant to be credible to frontier-AI eval people. Priorities:

1. Any agent harness can play through `fac`, and scores compare harness and model pairs (decision 46). Running inside Inspect AI (`inspect eval factobot/...`) is shelved, not removed.
2. Trustworthy scores: the harness observes completion itself, rules are enforced, versions are pinned, and the agent's sandbox exposes only the CLI.
3. Setup takes one command.
4. Recordings, timelapses and a leaderboard that people want to watch.
5. Many environments can run in parallel.

## Benchmark design

| # | Topic | Decision | Notes |
|---|---|---|---|
| 16 | Structure | Four tracks | **Staged ladder** (scored): one task per science tier, each starting from a fixed save that has a working factory for the tier below. **Full run to rocket** (flagship): starts from nothing, records milestone timestamps, and is the source of the headline videos. **Lab tasks**: short throughput goals on fixed maps. **Skill probes** (internal): narrow checks for building tools and diagnosing failures. |
| 17 | Clock | Score in game ticks | Each run also reports wall-clock time, tokens and dollar cost. |
| 18 | Milestone | Clock on first automated research, gated by sustained throughput | A tier's time is the tick at which labs first research with that tier's pack made by an assembler (hand-crafted packs never count). The tier only counts if machines then sustain ≥ N packs/min of it for 10 game-minutes within the stage cap. A value-weighted production score is recorded continuously. N per tier is still to be set. |
| 19 | Outages | Pause the game during API errors and retries | Slow calls that succeed still count against the agent. Pausing is driven by the model-call proxy (`inspect_swe` routes CLI agent model calls through Inspect; this is from its docs and still needs testing). Total paused time is capped and logged, and a run that exceeds the cap is void. Shelved with the Inspect path (decision 46): any harness now calls its model itself, so pausing for outages needs another way in, still open. |
| 20 | Budget | Game-time cap of 2x the human gap per ladder stage, plus a $ cap; 5 seeds per stage | A run stops at whichever cap it hits first. Results are reported as medians with confidence intervals. The slowest finishing score is therefore 0.5. |
| 21 | Human reference (score 1.00) | Average player: red 5 h, green 12 h, blue 25 h, purple + yellow 42 h, rocket 50 h, cumulative from a fresh start | Source and method in `docs/human-baselines.md`: HowLongToBeat median "main story" of 50 h (n=286) split by the per-tier time profile of 7 timed runs. No peaceful-mode adjustment. Provisional until decision 24 replaces it. |
| 22 | Ladder stages | Fresh start → red, red → green, green → blue, blue → purple + yellow, purple + yellow → rocket | Reference gaps 5, 7, 13, 17 and 8 h. Purple and yellow are one stage because neither needs the other in the tech tree and experts build them together. Military science is unscored: the rocket path never needs it. |
| 23 | Score | Per stage: reference time / agent time. Headline: geometric mean over stages | Above 1.00 is faster than an average player. An unreached stage scores half of what finishing exactly at the cap would (0.5 x 0.5 = 0.25 with 2x caps). The full run reports the same ratio per tier and for the rocket. |
| 24 | Own human baseline | Before launch, average players play our seeds and settings with the factobot mod recording milestone ticks | Validates or replaces the provisional anchors in decision 21 for the paper. |
