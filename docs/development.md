# Development

## Hosts

| Host | Role | Checkout |
|---|---|---|
| Desktop | Day-to-day development; Hyprland desktop for watching the game | `~/projects/factobot` |
| Server (also the CI runner) | Long eval runs and parallel environments | `~/projects/factobot` |

Any Linux machine can take either role.

## Setup

[mise](https://mise.jdx.dev) pins every tool (Rust, uv, StyLua, lua-language-server, Node and FMTK) and the Factorio version with its checksums. From a fresh checkout:

```bash
mise trust && mise install          # toolchain
uv sync --project python            # Python env in python/.venv
mise run fetch-factorio             # free headless server into ~/.cache/factobot/factorio/<version>
mise run check                      # everything CI runs
```

`mise tasks` lists the rest: `fmt`, `lint`, `test`, `luals-types`, `dev`, `playtest`, `agent-view`. `lint` generates lua-language-server types for the pinned Factorio API with FMTK (into `target/factorio-luals`), so a misspelled field or method on a game object fails lint before it reaches the game.

Screenshots, the live viewer and the camera also need Xvfb and Mesa (`sudo pacman -S --needed xorg-server-xvfb mesa` on Arch) and the graphical client: `mise run fetch-factorio -- --client` (needs `FACTORIO_TOKEN`).

Playtests also need bubblewrap, slirp4netns, nsenter (util-linux), iproute2 and nftables (`sudo pacman -S --needed bubblewrap slirp4netns util-linux iproute2 nftables` on Arch).

## Secrets

`.env.local` (gitignored, mode 600) is loaded by mise. Keys it may hold:

| Key | Used for |
|---|---|
| `FACTORIO_USERNAME` | factorio.com account name |
| `FACTORIO_TOKEN` | Service token for downloading the graphical client: `service-token` in `~/.factorio/player-data.json` after one login in the game, or from `https://auth.factorio.com/api-login` |
| `FACTORIO_MOD_API_KEY` | Mod portal API key, for publishing the mod later. It does not authorize game downloads. |

## Running a game by hand

```bash
cargo build
target/debug/fac daemon --seed 42             # foreground; Ctrl-C saves and stops the server
target/debug/fac status                       # in another shell
```

The daemon keeps its scratch state in `~/.local/state/factobot/run`: `server.log` is the game's log and `calls.jsonl` records every call with its game tick. Several daemons can run side by side with distinct `--run-dir`, `--socket`, `--rcon-port` and `--game-port`.

### Stopping a world

Stop a world by signalling its daemon: Ctrl-C, SIGTERM (`kill`, `systemctl --user stop`) or SIGHUP (closing its terminal). The daemon sends the server `/quit`, which writes `save.zip` in the run directory, waits up to 60 s for the server to exit, and kills it only after that; more signals while it waits change nothing. Never signal the server itself: Factorio saves on its first SIGTERM or SIGINT but quits mid-save on a second, which leaves the old `save.zip` and a partial `save.tmp.zip`. So the daemon starts the server in its own process group, where a terminal's Ctrl-C does not reach it, and with SIGTERM blocked, so a SIGTERM sent to every process of a systemd unit or session misses it. SIGINT sent to the server by hand still saves and quits. A daemon killed with SIGKILL takes its server with it, unsaved. The daemon has no autosave (decision 47), so a world is saved only when it stops, unless a playtest runs with `--autosave-minutes` (decision 48).

A world run as a systemd user unit (`systemd-run --user ...`) stops with a complete save under the default `KillMode=control-group` and `TimeoutStopSec=90`. `start_world` gives the daemon 90 s on exit. A playtest runner that gets SIGTERM, SIGHUP or a first Ctrl-C ends the run as `--timeout` does: it stops the agent, stops the world, and writes `summary.json` with `"stopped": true`. When the daemon got the signal too and is already saving, the summary's `end_tick` and packs come from the runner's last poll, at most 5 s earlier. When the signal lands while the world boots, the agent never starts, and if the daemon stopped before the runner's first poll, the summary's ticks and packs are null. A signal between an agent quitting and its resume ends the run the same way, with no resume. A terminal's Ctrl-C reaches the runner and the agent's sandbox, which share its process group, but not the world's daemon, which runs in a session of its own and saves when the runner stops it. A second Ctrl-C interrupts the runner at once.

### Dev tools

`fac dev` talks to the daemon's dev socket, which agents never get:

```bash
fac dev lua game.tick                         # read anything; expressions return their value
fac dev lua 'game.speed = 10'                 # change anything
fac dev lua - < setup.lua                     # multi-line scripts from stdin
fac dev hash                                  # deterministic fingerprint of the world
fac dev milestones                            # science packs by hand and machine, and when automated research began
fac dev snapshot /tmp/before.zip              # save the world (the server restarts)
fac dev reload                                # restart from the current state to load mod edits
fac dev screenshot --at 10,-4 --zoom 0.5 -o /tmp/base.png   # needs a daemon started with --camera
```

### Seeing the game

The daemon can keep two graphical spectator clients connected, and other machines can join with `fac watch`. The mod turns every player into a bodiless spectator, and puts it in the `factobot-spectators` permission group, which denies every input action except moving the view, remote view, changing the surface the view is on, toggling entity info and opening read-only windows such as production statistics (decision 38). Watching never changes the world (a live test checks the world hash with and without a camera).

- `--camera` renders on a private Xvfb display with Mesa llvmpipe, no GPU needed. `fac dev screenshot` and `World.screenshot` use it to write a PNG of any area, with alt mode and the warning icons a player sees (the camera runs with icon blinking off, so every shot has them). Read the PNG to check that a build looks the way the code says it does. The agent's own `fac screenshot` uses it too: what the agent's screen shows, centred on its body (decision 67). A playtest started with `--camera` gives its agent that command; the sandboxed `fac` writes the PNG into the agent's working directory, `/home/agent/work`, and prints the whole result with `path` in place of the image data, so each preset gets a file-reading tool that shows images besides its shell: Claude Code's `Read` and omp's `read`. A custom harness needs one of its own. Only `mise run rocket` turns the camera on (decision 77); without one, `fac screenshot` fails as `unavailable`.
- `--viewer` opens a normal window on the current display. A missing or unusable `DISPLAY` fails before Factorio starts. `mise run dev` (from a terminal on the desktop) starts a persistent world with a viewer and a camera; pan with WASD, zoom with the mouse wheel. Viewers reconnect after `fac dev reload`.
- `fac watch HOST` opens that window on another machine, joined to a daemon started with `--listen <address>`. The daemon's game port then listens on that address instead of localhost (Factorio binds one address, so its own camera and viewer connect there too); RCON stays on localhost. To watch a world on the server from the desktop, run `mise run serve` on the server (it listens on the server's tailnet address) and `HOST=<address>:34197 mise run watch` from a terminal on the desktop. If `DISPLAY` is unset or the X server does not accept a connection, `fac watch` exits before Factorio starts. `HOST` is required, and a missing port defaults to 34197, which is not the port a playtest or rocket run prints. Both checkouts must have the same `mod/factobot`, file for file, or Factorio refuses the join with a mod mismatch. The window does not follow a `fac dev reload`; run `mise run watch` again.

`mise run watch` and `mise run dev` open Factorio's window on the desktop's Hyprland session. The client attaches only when that session's display variables are in the environment that starts it. A terminal opened on the desktop already has them. Any other shell on that host, such as ssh, a user service, or an agent session that did not inherit the desktop, has to export them first, or the client cannot attach: `DISPLAY=:0` and `WAYLAND_DISPLAY` set to the session's socket. The socket is the `wayland-*` name in `/run/user/$(id -u)/`, often `wayland-1`. `DISPLAY=:0 WAYLAND_DISPLAY=wayland-1 HOST=<address>:<port> mise run watch` joins a world whose address the run printed on stderr. The same two variables go in front of `mise run dev`.

Clients load in about 5 s from a shared sprite atlas cache, kept in `atlas-cache/` beside the client's `bin/`; each cache is 1.1 GB to 1.6 GB. Without it, loading sprites takes about 45 s of every CPU thread, and minutes on a loaded machine; that once pushed a `fac watch` join past its 180 s limit in CI. Factorio builds a different atlas for each renderer and rejects one built by another, so the camera (llvmpipe under Xvfb) publishes to `atlas-cache/xvfb/` and windowed clients (the viewer and `fac watch`) to `atlas-cache/window/`. A client tries its own kind's cache first, then the other kind's (a window under `xvfb-run` renders like the camera); if both are missing or rejected, it builds one and publishes it to its own kind's directory, replacing the cache there. A rejected cache of the other kind stays, since the renderer that built it may still use it. The daemon's camera and viewer publish once they have joined; `fac watch` publishes when you close its window, if it got as far as loading the game, so quitting it with Ctrl-C publishes nothing. So the caches fill themselves, once per machine, renderer and Factorio version, and a Mesa or GPU change costs one rebuild. If a mod ever ships images, clients skip the cache. Their logs are in `<run dir>/factobot-camera/` and `<run dir>/factobot-viewer/`, and for `fac watch` in `~/.local/state/factobot/watch/<name>/`.

### Playtests

`mise run playtest -- playtests/smoke.md --model sonnet` boots a fresh world and runs an agent harness headless against it: Claude Code by default, omp with `--agent omp` (`--model` is passed to the harness, which resolves it its own way; omp's `sonnet` is a fuzzy match), or any other command given after `--`, where `{prompt}` in an argument becomes the prompt: `mise run playtest -- playtests/smoke.md --env MY_API_KEY -- my-agent --print {prompt}`. `--env NAME` passes a host variable to a custom command and `--expose PATH` mounts a host path read-only at the same path, for a harness that needs more than its binary. A `.lua` file of the same name next to the task (`playtests/power-and-research.lua`) runs in the world first, to give the agent items or research so the playtest covers only the new commands. The run directory (`target/playtests/<task>-<time>-<random>/`) holds `transcript.jsonl` (the harness's stdout), the world's `calls.jsonl`, and `summary.json` with the agent, `fac` calls and errors, and the final answer. Turns and cost come from Claude Code's own report and are null for other harnesses; omp's final answer is its last message. `response_bytes` adds up the size of the daemon's responses to the agent's calls, as compact JSON, in total and per method: what the agent's commands returned before it filtered them with its own tools. The runner polls the world about every 5 s of wall time while the agent plays. The game keeps no record of when research finished, so `research` lists each technology finished during the run with the tick of the first poll that saw it, up to one poll late. `lab_use_by_minute` holds, for each game minute a poll fell in, the tick and how many packs of each kind labs had used so far. Use it on each new command to see whether an agent can find and use it from `--help` alone.

`fac ... --wait` can block for up to 600 s, so each preset's shell is set to let it: Claude Code gets `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` of 660000 (by default it moves a Bash call to the background after 120 s), and omp gets `bash.autoBackground.enabled: false` in its `~/.omp/agent/config.yml` (by default it moves a call to a background job after 60 s). omp's own per-call timeout of 300 s is not a setting; the model can ask for a longer one on each call.

Every harness runs in the same bubblewrap sandbox (`python/src/factobot/sandbox.py`, decision 46), so no harness's own permission rules have to hold it, and each gets its own shell in it. Playtests need `bwrap`, `slirp4netns`, `nsenter` and `ip` in `/usr/bin`, and `nft` for omp, and check for them before the world boots. Inside, the agent sees `/usr` and `/etc` read-only, a private `/tmp`, `/dev` and `/proc`, a network of its own that slirp4netns connects to the internet, and:

- `/opt/factobot/bin/fac`, the agent's build of `fac` (`target/debug/fac-agent`, decision 64), which has no `dev`, `daemon`, `watch` or `--dev-socket`; the harness's `fac` is not in the sandbox;
- `/run/factobot/fac.sock`, the world's agent socket, alone in its directory, with `FACTOBOT_SOCKET` pointing at it;
- `/opt/agent/bin/<name>`, the harness binary;
- `/home/agent`, a throwaway home deleted after the run, with the empty working directory `/home/agent/work`. For Claude Code it holds a copy of the Claude.ai login from `~/.claude/.credentials.json` (the `claudeAiOauth` entry only). If Claude Code refreshes that login during a run, the refreshed tokens go back to the host's file afterwards, unless the host's changed meanwhile. Since the agent can write its home, the harness reads the file without following symlinks and takes back only the access and refresh tokens and their expiry times, each of the right type, and only when the access token expires later than the one it gave; every other field stays the host's. These checks stop a broken or stale file, not a deliberate swap: every field they look at is one the agent can write, and the login file names no account, so an agent that logs in to another Claude account inside the sandbox can hand those tokens back, and the host's Claude Code then runs as that account until someone logs in again. That gives the agent more than it had. A copy of the host's refresh token already lets the agent spend the host's Claude account from anywhere it can reach the internet, so it is a secret worth guarding in its own right, but it stays inside that one account and buys no way out of the sandbox; after a swap, the host's Claude Code, which runs outside the sandbox, loads what the other account brings. Claude Code makes an account's claude.ai connectors (MCP servers) available automatically. Since 2.1.273 it also downloads the plugins turned on for the account on claude.ai, by the account's owner or by its organization, each time it starts in a terminal, and loads their hooks (shell commands), MCP servers, skills and agents with the trust of a plugin the user installed; Claude Code's plugin loading reference asks for no organization or plan, and `"syncClaudeAiPlugins": false` in the host's `~/.claude/settings.json` turns the sync off. And it fetches the server-managed settings of the account's Team or Enterprise organization, which can carry hooks and environment variables; since Claude Code 2.1.316 those settings apply without an approval prompt. So for an agent that controls another account, with or without an organization, a swap is a way out of the sandbox, the one known gap in the "Agent sandbox" invariant. The write-back stays for now, because without it a run past about 8 hours can leave the host logged out; whether to keep it at that cost is still open (decision 46). After a playtest with an agent you do not trust, log the host in again before its next session: `claude auth logout`, then `claude auth login`, which replaces both tokens. No lookup stands in for that. The harness takes each token field on its own, so the agent can hand back the host's own access token beside another account's refresh token. Asking who the access token belongs to (`jq -r '"Authorization: Bearer " + .claudeAiOauth.accessToken' ~/.claude/.credentials.json | curl -sS --fail-with-body -H @- -H 'anthropic-beta: oauth-2025-04-20' https://api.anthropic.com/api/oauth/profile`, then `account.email`) names the host's account in that case, and the login moves to the other account only later, when Claude Code refreshes it with the refresh token. So that lookup can show a swap and cannot rule one out. `claude auth status` and `/status` show even less: both read the `oauthAccount` cached in `~/.claude.json`, which a token swap leaves untouched, so they still name the account the host had before. Do not open `claude` on the host before logging in again, and close any session already running there before the playtest ends: starting a session loads the swapped account's managed settings first and syncs its plugins, hooks among them, and a session that is already open polls for credential changes while it runs, so the swapped login can reach it before anyone looks. For omp it holds a copy of `~/.omp/auth-broker.token`, and `OMP_AUTH_BROKER_URL` comes from the environment, so omp gets its credentials from the auth broker.

It does not see the repository or any worktree, the run directory (`config.ini`, `calls.jsonl`, `dev.sock`, saves), `/run/user`, the rest of `$HOME` (host settings, CLAUDE.md, AGENTS.md, skills, MCP servers, other sessions), or other processes: `--unshare-pid` gives the sandbox its own `/proc`, so the server's command line with the RCON password is out of sight. Nor does it reach the host's abstract Unix sockets (the camera's Xvfb listens on one) or anything on the host's localhost, since the sandbox has its own network namespace and slirp4netns runs with `--disable-host-loopback`. slirp4netns itself runs as the host user outside the sandbox, so it also runs with `--enable-seccomp`, which limits the syscalls a libslirp bug could use; `--enable-sandbox` cannot be used, since it needs `setegid(0)`, which fails in bwrap's user namespace, where only the user is mapped. It cannot reach the host's other addresses or anything on the LAN or tailnet either, where `--listen` puts the game port: before the agent starts, the runner adds unreachable routes in the sandbox's namespace for each of the host's IPv4 addresses and for 10.0.0.0/8, 100.64.0.0/10, 169.254.0.0/16, 172.16.0.0/12 and 192.168.0.0/16 (with `nsenter --keep-caps` and `ip`), and the agent has no capabilities to remove them. The one exception is omp's auth broker, which usually listens on this host's tailnet address: for omp the runner resolves the host in `OMP_AUTH_BROKER_URL` to its IPv4 address, routes that address out through slirp4netns, and adds nftables rules in the namespace that accept TCP to the broker's port and reject everything else to that address, so a game port on the same address stays out of reach. The agent can read its harness's login, since the harness runs as the agent.

`mise run playtest-red` plays ladder stage 1 (a fresh map to automated red science) with Claude Code and `opus` by default (`HARNESS=`, `MODEL=` and `SEED=` change them; the harness is not picked with `AGENT=`, because agent shells such as omp set `AGENT=1`), at game speed 1. With `HARNESS=omp` the model defaults to `claude-opus-5-5`, named in full as for `mise run rocket` below. The game port listens on this host's tailnet address, and the run prints `watch with: fac watch <address>:<port>` on stderr; watch it from the desktop with `HOST=<address>:<port> mise run watch` and the Hyprland display variables under Seeing the game, from a checkout with the same `mod/factobot`. `--until automation-science-pack` has the harness stop the agent once labs research with a machine-made pack (decision 43), and `summary.json` then holds `milestone_tick` and the packs made and used; the 36000 s timeout is decision 20's 2x cap on the 5 h reference. The exit status is 0 only when the harness saw the milestone. A save keeps the milestone ticks it reached, so `--until` with a `--save` (or a setup) that has already reached the milestone fails before the agent starts.

`--save` starts a playtest from a copy of a save instead of a new map, so a fresh agent can take over where a run stopped: each run leaves `world/save.zip` in its run directory, written when the server quits. `mise run playtest -- playtests/keep-going.md --model opus --save target/playtests/<run>/world/save.zip --timeout 36000 --listen $(tailscale ip -4)` continues a finished red-science run toward green science with no milestone to stop it, so unless the agent quits, `--timeout` ends the run (1800 s when not given). The new agent remembers nothing of the old one and has to look around first. Its `summary.json` records the save's absolute path under `save` and leaves `seed` null, since no map was generated from `--seed`. A save carries its tick and pack counts into the run, so `end_tick` and `packs` include the old run's; `start_tick` and `packs_at_start` hold them as the agent started, and the new agent's share is the difference.

`--timeout` is seconds of the agent's own run, counted after the world has booted (1800 when not given). The deadline is the moment the agent starts plus the timeout. It is a duration, and the harness has no unlimited value. `0` (`--timeout 0`, and `TIMEOUT=0` on `mise run rocket`, which the task's `${TIMEOUT:-172800}` passes through because any non-empty value replaces the default) is not an uncapped run: the deadline is already due, so the agent is stopped as soon as it starts and `summary.json` records `"timed_out": true`. A run that should continue until its goal, or until someone stops it, needs a cap it will not reach, such as `--timeout 999999999` or `TIMEOUT=999999999`.

`--until rocket` stops the agent at the first rocket launch, read from the dev socket's `milestones` (`rocket_launched_tick`). With `--until`, an agent that quits before the goal and before `--timeout` is resumed in the same conversation with a short message saying the goal is not reached yet, up to `--max-resumes` times (10 by default). Claude Code continues with `--resume <session_id>` and omp with `--resume <id>`, each taking the id from its own output; both save their sessions in the sandbox home, which lives for the whole run. A custom command has no session the runner knows, so it starts again with the task and that message. An agent process that exits non-zero within 30 s without a single `fac` call failed to start rather than quit (omp exits so when it cannot reach its auth broker); after two of those in a row the runner stops resuming, prints why on stderr, and puts the last line the agent wrote under `agent_failed` in `summary.json`. The transcript keeps growing across resumes, so `mise run agent-view` follows on, and `summary.json` lists each resume under `resumes` with the agent's exit code, the tick and the wall time.

`--autosave-minutes N` saves the world every N minutes of wall time while the agent plays, with `game.server_save`, to `world/write-data/saves/autosave-1.zip`, `autosave-2.zip` and `autosave-3.zip` in the run directory, in turn, so a save cut short leaves the other two. Each is a normal save: `--save target/playtests/<run>/world/write-data/saves/autosave-<n>.zip` continues from it, and `summary.json` lists the ones on disk with their ticks under `autosaves` (the stderr log names each as it is written). The newest is the one with the latest modification time.

`mise run agent-view` follows the most recently started run under `target/playtests/` (by the mtime of the run's `started` file, which the playtest touches as it begins) from a second terminal on the same host (`mise run agent-view -- RUN_DIR` picks one): the agent's messages, each `fac` command it runs and the first lines of what it returned, with errors in red. It prints the run so far, then follows it and prefixes each new line with the game tick of the latest `fac` call. It only reads the run's files, so stopping it leaves the run alone. It reads Claude Code's stream-json and omp's JSON events, telling them apart by their shape. For a harness whose output it does not know, it shows each `fac` call from `calls.jsonl` instead (method, parameters, and the result or error), so any agent can be watched. omp shows the model's reasoning in dim text; recent Claude models leave the thinking text out by default, so Claude Code's thinking blocks arrive empty and its short messages between commands are all there is.

### Rocket run

`mise run rocket` is the rocket track (decision 77): omp with `claude-opus-5-5` by default plays `playtests/rocket.md` from a fresh map to a rocket launch, with the `skills/factorio-rocket` skill installed and a camera, so the agent has `fac screenshot` and can look at its factory. Neither the skill nor the prompt knows anything about a map: no seed, no coordinates. The skill's layouts are tested blocks given as offsets from an anchor the agent picks, and its first rules are that the factory runs without the agent's hands and that a stall is fixed before anything else is built. The model is named in full because omp matches a short name such as `opus` fuzzily, and in the sandbox's empty home `opus` picked `claude-opus-4-5`. It runs headless with `--until rocket`, a 48 h `--timeout`, up to 100 resumes and an autosave every 10 minutes. `HARNESS=claude`, `MODEL=`, `SEED=` and `TIMEOUT=` change the harness, model, map and time cap in seconds (`TIMEOUT=3600 mise run rocket` for a one-hour test; `AGENT=` is not used, since agent shells set it). `TIMEOUT=0` ends the run at once: the deadline is the moment the agent starts plus the timeout, so 0 is not an uncapped run, as described under Playtests. An overnight run with no time limit uses a large second count that the cap will not reach, as in `TIMEOUT=999999999 mise run rocket`; it still ends at the rocket, after 100 resumes, after two failed starts in a row, or when stopped by hand. `SAVE=target/playtests/<run>/world/write-data/saves/autosave-<n>.zip mise run rocket` continues a stopped attempt from an autosave, or from the `world/save.zip` a finished run leaves. Ctrl-C (once), `systemctl --user stop` or a closed terminal ends the attempt cleanly: the agent stops, the world saves, and `summary.json` says `"stopped": true`. A run started under `nohup` keeps ignoring the hangup, so it outlives the terminal. Like `playtest-red`, the game port listens on the tailnet address and the run prints `watch with: fac watch <address>:<port>` on stderr: watch the game from the desktop with `HOST=<address>:<port> mise run watch` (and the Hyprland display variables under Seeing the game), and the agent with `mise run agent-view` in a second terminal on this host. The agent's screenshots stay in its working directory, which is gone with the sandbox home when the run ends.

The prompt has the agent keep `notes.md` in its working directory: its map, base plan and open problems, since its context is cut during a long run. The runner copies that file to the run directory at every autosave and when the run ends (decision 85). To continue a stopped run with a new agent, give both the save and the notes: `SAVE=target/playtests/<run>/world/write-data/saves/autosave-<n>.zip NOTES=target/playtests/<run>/notes.md mise run rocket`. The rocket run is started by hand; CI never runs an agent.

`--skill DIR` (repeatable) copies a skill directory with a `SKILL.md` into the sandbox home, where the harness finds it on its own: `~/.claude/skills/<name>/` for Claude Code and `~/.omp/agent/skills/<name>/` for omp. Nothing else from the repository goes in. Claude Code reads `~/.claude/skills` only with the `user` setting source, so with skills it runs with `--setting-sources user,local` (the sandbox home has no other user settings), `--tools Bash,Read,Skill`, and without `--disable-slash-commands`, which turns skills off; its own bundled skills then show as well. omp runs with `--skills <names>`, a filter on skill names, in place of `--no-skills`. `summary.json` lists the skills under `skills`. A custom command after `--` takes no `--skill`.

### Leaderboard

`mise run report -- target/playtests -o target/reports` reads every `summary.json` under the paths you give (default `target/playtests`) and any Inspect `.eval` log, and writes `leaderboard.md` and `leaderboard.html`. The HTML charts are inline SVG, so the file stands alone. A benchmark run scores decision 23 from `start_tick` and `milestone_tick`: cumulative reference hours on a fresh map, the stage gap when the run started from a save. A timeout with no milestone, or a milestone after twice the reference time, scores 0.25. A run that was stopped, or whose agent quit first, stays out of the median. Runs that installed a skill are listed apart and are not scores (decisions 48, 77 and 87). `python -m factobot.report` is the same command.

### Benchmark runs

The Inspect AI path below is shelved, not removed (decision 46): the benchmark is the world and `fac`, played by any harness through the playtest runner above. The code and its tests stay in place.

`uv run --project python --extra anthropic inspect eval factobot/red_science --model anthropic/<model> -M max_retries=0` runs ladder stage 1 on seeds 1 to 5 (decision 44). `-M max_retries=0` turns off the provider SDK's own retries for the `anthropic` and `openai` providers (xAI's provider takes `-M disable_retry=true` instead; Google's SDK client has no such switch), so that Inspect retries the failures the provider counts as retryable and the game pauses from the first retry on, the first failed attempt running in game time (decision 45). `-T 'seeds=[1]'` picks fewer seeds, `-T throughput=N` applies decision 18's gate, and `-T pause_cap=S` voids a run paused longer than S seconds for model outages. A void or broken seed shows as an error in the log while the other seeds play on; the metrics cover the seeds that scored. Inspect reaches each model provider through that provider's SDK: `--extra anthropic` and `--extra openai` install the locked ones for `anthropic/...` and `openai/...` models, and `--with <package>` adds another provider's (Inspect's error names the package). A stage runs in real time for up to its game-time cap (10 h for red science), so cap a trial run with Inspect's `--time-limit`. The `fac` binary comes from `FACTOBOT_FAC`, else `PATH`, else the checkout's own `target/debug/fac` (`cargo build`). `inspect view` shows each run's transcript and score; the score's metadata has `start_tick`, `end_tick` and `stage_ticks` (the ticks the stage took), `paused_seconds` (seconds paused for outages) and `outages`.

## Test worlds

`factobot.harness.start_world` boots a throwaway world with its own ports, sockets and run directory, and stops it afterwards. Development scripts and checks by hand use it to set up an exact situation and observe the result:

```python
from factobot.harness import start_world

with start_world(seed=7, speed=20) as world:      # or save="fixtures/x.zip"
    world.lua('game.surfaces[1].create_entity{name="wooden-chest", position={0, 0}, force="player"}')
    world.run_to_tick(900)                         # pause and advance exactly to a tick
    print(world.agent.status(), world.world_hash())
```

`run_ticks` and `run_to_tick` pause the game and step it with `game.ticks_to_run`, so assertions land on exact ticks however fast the machine is. `speed` runs timed actions faster than real time. `camera=True` adds the screenshot client (`world.screenshot(path, at=(x, y))`, and `world.agent.screenshot(path)` for what the agent's screen shows). A failed daemon leaves its run directory in `/tmp/factobot-world-*` with `server.log`, `daemon.log` and `calls.jsonl`.

A world stops with the process that started it, even when that process is killed outright and never reaches its cleanup: the harness has Linux send the daemon SIGTERM when its parent dies, and the daemon stops its server and clients. The signal follows the thread that called `start_world`, so open worlds from a thread that outlives them. The camera client renders every frame on the CPU with no frame-rate cap, over 200% of a core while idle, so it runs at `nice` 15. Nice only ranks processes within one scheduling group: the camera's cpu cgroup, or, when the cpu controller is off, its session's autogroup, and the harness starts each world in a session of its own. The camera yields to its own server and to whatever shares its group, but not to processes in other systemd slices, services or sessions, which it competes with at normal weight.

The server and the CI runner share their cores with other projects. `mise run worlds` lists the worlds running on the machine with the worktree they came from, their age and CPU, and the load average; check it before starting worlds. A world whose starter is gone shows as `ORPHAN`, and `mise run worlds -- --kill-orphans` stops those.
